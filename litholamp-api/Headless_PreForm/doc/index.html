Headless PreForm

Headless PreForm's Cli interface is very simple. It has one command called run, which should be followed with a path to a JSON file.

> HeadlessPreForm run path/to/your/top/level/file.json

The file contains all the necessary information the application needs in order to execute the right action with the right input data. You can read further about this in the next chapter.

Additionally, the application also has some flags, with which the user can specify the format of the progress output.

> HeadlessPreForm run path/to/your/top/level/file.json --progress-as-json

and if needed, specify the location where the progress should be written instead of the standard out.

> HeadlessPreForm run path/to/your/top/level/file.json --progress-as-json --log_file=path/to/file

Actions

The application supports 3 main actions: prepare, slice and print.

type Actions = Prepare | Slice | Print;

Prepare

Prepare starts from a printer type and a material. It collects models from various sources and builds up a scene for further processing. Its job is to position the models, orient and scale them as necessary. It also generates the support structure and lays out the result on the build platform. The most complex action out of three.

The output is a FORM file which can be loaded in PreForm or used as input in other actions of the Headless PreForm application.

type Prepare = {
    action: "prepare", // action to be performed
    version: 1, // JSON schema version

    input: FileOrInline<SceneSettings>, // see the Scene Settings section below
    output: FormFilePath, // FROM file path and name for the output

    printer_address?: PrinterAddress, // for parameter detection
    login_credentials?: LoginCredentialsPath // if remote printer or printer group is used
    autosave_filepath?: FormFilePath // the scene is saved here if the prepare task fails
}

You will find some constant fields in the documentation such as action and version. Their purpose is to tell what kind of objects are we talking about and what version of the schema is used to describe them.

The two optional fields printer_address and login_credentials are used when you want to connect to a printer and read some information from that (machine type, current material). This is described later in the scene settings section.

Examples

A short example with only the required properties:

{
    "action": "prepare",
    "version": 1,
    "input": "scene-settings.json",
    "output": "circle.form"
}

A more detailed one with all properties:

{
    "action": "prepare",
    "version": 1,
    "input": {
        "kind": "SCENE_SETTINGS",
        "version": 1,
        "global": {
            "kind": "GLOBAL_SETTINGS",
            "version": 1,
            "machine_type": "Detected",
            "material": {
                "type": "Detected",
                "thickness_mm": 0.1
            },
            "layout": "auto"
        },
        "models": [
            {
                "model_file": "circle.stl",
                "settings": {
                    "kind": "MODEL_SETTINGS",
                    "version": 1,
                    "scale": 1.0,
                    "units": "mm",
                    "orientation": [1,1,1],
                    "support_settings": {
                        "raft_type": "FULL_RAFT",
                        "density": 1,
                        "touchpoint_size_mm": 0.3,
                        "internal_supports_enabled": false
                    }
                }
            }
        ]
    },
    "output": "circle.form",
    "printer_address": "HabitualSnail",
    "login_credentials": "login-credentials-with-token.json"
}

JSON is a hierarchic language, and Headless PreForm's input description can grow. To make it easier to reuse and change settings scattered around in many places most settings can be used in two forms. When you see FileOrInline<X> in the documentation it means that you can either write X in place or create a file containing it and just refer to it with the file path. In the above two examples, you can see an example for both cases for the input property.

Slice

Slicing is a computationally intensive process that disassembles 3D geometry into thin layers ready for 3D printing. As the name suggests Headless PreForm's slice action is responsible for this step in the printing pipeline. The output is a collection of .flx files (one for each layer of the print) and corresponding metadata wrapped in a .tar.gz file with .flz extension. This can be fed into the print action later.

The exact outcome of the algorithm depends on the material and the machine type, and optionally on the actual printer instance as well. This is because different 3D printers have different calibration needs which can be taken into account during the slicing process. This setting is also known as OBO.

The corresponding JSON file has the following properties:

type Slice = {
    action: "slice", // action to be performed
    version: 1, // JSON schema version

    input: FormFilePath | FileOrInline<SceneSettings>,
    output: FlzFilePath, // FLZ file path and name for the output

    calibration_settings?: TODO, // TODO
    printer_address?: PrinterAddress, // for parameter detection
    login_credentials?: LoginCredentialsPath // if remote printer or printer group is used
    autosave_filepath?: FormFilePath // the scene is saved here if the prepare task fails
}

Slicing can start directly from a FORM file or - based on the provided input - delegate to the prepare action first.

Print

The models are prepared, the scene is sliced, we are ready to create something to hold in our hands. The print action uploads the job to the printer and returns a print_job_id that will identify it during the manufacturing process.

type Print = {
    action: "print", // action to be performed
    version: 1, // JSON schema version

    input: FlzFilePath | FormFilePath | FileOrInline<SceneSettings>,

    calibration_settings?: TODO, // TODO
    printer_address: PrinterAddress, // for parameter detection and upload destination
    login_credentials?: LoginCredentialsPath // if remote printer or printer group is used
    autosave_filepath?: FormFilePath // the scene is saved here if the prepare task fails
}

Printing can start directly from an FLZ file or - based on the provided input - delegate to the slice or prepare actions first.

Estimate

We also might want to get some estimations of the given job before we print it. The estimation action estimates the print time and material usage of the given scene and prints to the output.

type Print = {
    action: "estimate", // action to be performed
    version: 1, // JSON schema version

    input: FormFilePath | FileOrInline<SceneSettings>,

    printer_address?: PrinterAddress, // for parameter detection
    login_credentials?: LoginCredentialsPath // if remote printer or printer group is used
    autosave_filepath?: FormFilePath // the scene is saved here if the prepare task fails

Estimation can start directly from a FORM file or can create a scene from scratch via the provided settings file.

Settings

With different settings files we can specify different input properties with which we can define the result of the actions. The following subchapters talk about all the possible settings we have control over.

Scene Settings

Scene settings define the input to the whole printing pipeline. The global settings section selects a machine type and the required material. The models section enumerates what to be printed and how.

type SceneSettings = {
    kind: 'SCENE_SETTINGS', // settings type identifier
    version: 1, // JSON schema version

    global: FileOrInline<GlobalSettings>, // see the Global Settings section below
    models: Model[] // see below for more information
}

Model[] is a list of an inplace JSON object containing a path to a model file and settings what to do with it:

type Model = {
    model_file: ModelFilePath, // OBJ, STL or FROM file path with name
    settings: FileOrInline<ModelSettings> | Patterns
}

In case of OBJ and STL files, the file contains just a single model. This is simply set up as written in the Model Settings.

FORM files have special treatment. A FORM file can potentially contain many models, each of which will be imported. The models in the FORM files might already have supports attached to them. If the desired material and machine combination and the other parameters make it possible, the supports will be kept and reused in later steps. In some cases, however, the support needs to be regenerated. This can occur when a different material is used or the models' scale or orientation changes.

It's also worth mentioning that the FORM file's material and machine settings are not imported. It is checked to decide whether the supports can be kept but otherwise doesn't affect the final outcome.

{
    "kind": "SCENE_SETTINGS",
    "version": 1,
    "global": "global-settings-with-explicit-material.json",
    "models": [
        {
            "model_file": "spheres.form",
            "settings": {
                "kind": "MODEL_SETTINGS",
                "version": 1,
                "scale": 1.0,
                "units": "mm",
                "orientation": [1,1,1],
                "support_settings": {
                    "raft_type": "FULL_RAFT",
                    "density": 1,
                    "touchpoint_size_mm": 0.3,
                    "internal_supports_enabled": false
                }
            }
        }
    ]
}

If you import multiple models from a FORM file, you can apply different settings to them based on the models' name. This is not mandatory, as we have just seen, but you have the option to do it. Let's say you have a nice robot in a FORM file with parts head, body a left wheel and a right wheel and you want to handle the wheels specially:

{
    "kind": "SCENE_SETTINGS",
    "version": 1,
    "global": "global-settings-with-explicit-material.json",
    "models": [
        {
            "model_file": "robot.form",
            "settings": {
                "patterns": {
                    "head": "upper-part-settings.json",
                    "body": "upper-part-settings.json",
                    "*wheel": "wheel-settings.json"
                }
            }
        }
    ]
}

When Headless PreForms processes the models it checks the keys of the patterns object and compares them to the model's name. You can use wildcards such as * and ? to treat some models the same way, as we have done with the wheels above. Keep in mind though that each model should have exactly one matching line, otherwise an error will be reported.

For completeness, the rigorous definition of the Patterns type is the following:

type Patterns = {
    patterns: {
        [wildcardPattern: string]: FileOrInline<ModelSettings>;
    }
}

Global Settings

Global settings are part of the scene settings. It is responsible for the machine and material selection and layout settings.

type GlobalSettings = {
    kind: 'GLOBAL_SETTINGS', // settings type identifier
    version: 1, // JSON schema version

    machine_type: MachineType, // see below for more information
    material: MaterialDescription, // see below for more information
    layout: "auto" | "none", // should auto layout be triggered?
    layout_settings?: PackingSettings, // see below for more information
    seed?: number, // specify a seed for the algorithms used
    repair_behavior?: "repair" | "error" | "ignore if raw scan" | "ignore" // behavior to use when loading a broken model
}

Where MachineType is either read from the printer or one of the supported machines:

type MachineType = "Detected"
                 | "Form 2"
                 | "Form 3" | "Form 3B" | "Form 3L" | "Form 3BL"
                 | "Form 4" | "Form 4B" | "Form 4L" | "Form 4BL"
                 | "Fuse 1" | "Fuse 1+ 10W" | "Fuse 1+ 30W"
                 | "Fuse 2L";

MaterialDescription can either be read from the printer, explicitly set or one can specify the path to the material file itself.

type MaterialDescription = DetectedMaterial | ConcreteMaterial | PathToMaterialFile;

type PrintSetting = string; // see below for more information
type Thickness = "adaptive" | number; // see below for more information

type DetectedMaterial = {
    type: "Detected",
    printSetting: PrintSetting, // optional
    thickness: Thickness
};

type ConcreteMaterial = {
    type: {
        name: string, // the version-less material code such as FLGPBK
        version: number, // version of the material, e.g.: 4
    },
    printSetting: PrintSetting, // optional
    thickness: Thickness
};

For the first two cases need the desired layer height or thickness as well. This can be set in millimeters or let algorithmically decided if left on adaptive. Note that the supported layer heights vary from material to material, and not every material can be used in adaptive mode.

If Detected is used in the first setting above, the printer must be set in the corresponding action description.

The parameter printSetting is optional. With this parameter users can control which setting of the selected material file the user wants to use. This setting defaults to the default setting for each material, but one might want to use legacy or beta settings for example and in such case it needs to be explicitly set.

The third option is only usable for debug / testing builds, in other words it is only internally available. Instead of detecting the material from the printer or explicitly set it, one can specify the path to the material file itself, which sets the name, version, print setting and thickness automatically. It is important to mention that the material file at the specified path needs to be fully inflated to contain all knobs.

PackingSettings contains parameters related to the 3D AutoLayout algorithm (also known as Packing).

type PackingSettings = {
    kind: "PACKING_SETTINGS"
    version: 1

    // Minimum (non-zero) distance between models in the scene.
    model_spacing_mm: number,

    // Restrictions on rotational transformations applied to models.
    rotation_restriction: "NoRestriction" | "OnlyAroundZ" | "LockRotation"
};

note: PackingSettings may only be specified when using AutoLayout on a job intended for an SLS printer.

Model Settings

Model settings are part of the scene settings' models section enumerates. It is responsible for the units, scale, orientation and support settings.

type ModelSettings = {
    kind: "MODEL_SETTINGS", // settings type identifier
    version: 1, // JSON schema version

    copies?: integer,
    units?: "mm" | "in" | "detected",
    scale?: number,
    orientation?: "auto" | [number, number, number],
    support_settings?: SupportSettings
};

It should be noted that Model Settings are optional. If they aren't supplied, appropriate values will be inferred based on the context.

The copies property indicates the number of additional copies of the model that should be generated. Duplicate models are placed as new models in the scene, at the first valid location. The default number of copies is 0, with only the original model being added to the scene.

STL and OBJ files don't have units associated with them. The default setting for units is detected. In case of STL and OBJ files, this means "mm", unless the model is very small, in which case the user will be warned, and "in" will be automatically selected. If this still doesn't help one can further change the size of the model with setting the scale field as well.

Although models coming from FORM files have the associated units, one can still override it with the above settings. The capitalization and spelling of units is somewhat flexible, for example, the full word "Millimeters" is accepted.

The orientation property can be either set to auto for automatically finding the optimal orientation for the given model or an explicit vector can be set for an exact orientation.

For more information on SupportSettings read the next chapter.

Examples

Here is an example of the model settings JSON file:

{
    "kind": "MODEL_SETTINGS",
    "version": 1,
    "scale": 1.0,
    "units": "mm",
    "orientation": [1,1,1],
    "support_settings": {
        "raft_type": "FULL_RAFT",
        "density": 1,

Support Settings

Support settings is part of the model settings. It is responsible for all the properties which affect the result of the support generation.

type SupportSettings = {
    raft_type: "NONE" | "FULL_RAFT" | "MINI_RAFTS",
    raft_label_enabled?: boolean,
    density?: number,
    touchpoint_size_mm?: number,
    internal_supports_enabled?: number,
    raft_thickness_mm?: number,
    slope_multiplier?: number,
    height_above_raft_mm?: number,
    z_compression_correction_mm?: number,
    early_layer_merge_mm?: number
};

Specifying printers

type PrinterAddress = PrinterSerialName | IPAddress | PrinterGroupId

Some actions support automatic parameter detection from a Formlabs machine such as the printer's type or the material it contains. Other actions need to connect to a printer to achieve their purpose. These actions have a printer_address and a login_credentials field.

The printer_address can contain a remote printer's serial name, a printer group's name or id, a local printer's serial name or a local printer's IP address. If a remote printer or printer group is used the login_credentials field should point to a JSON file with valid login credentials for the Formlabs Dashboard.

Login Credentials

When a remote printer or printer group needs to be connected, you should provide some Formlabs Dashboard login credentials. The structure needs to be saved into a separate JSON file and included from that.

type LoginCredentialsWithToken = {
    access_token: string,
}

Here is an example login credentials JSON file:

{
    "access_token": "some token"
}

Alternatively one can provide his username (or email) and password pair as well:

type LoginCredentialsWithPassword = {
    username: string,
    password: string
}

Other

Thumbnail Generation

Headless PreForm while it is a console application it will try to generate the thumbnail image of the job if it can obtain an OpenGL context, like regular PreForm would. If it fails to obtain an OpenGL context currently it will crash PreForm (in the future this will turn into a warning). On the other hand if it successfully obtains the OpenGL context and fails to generate the thumbnail it won't fail the print generation as regular PreForm would do. Instead, it will write a warning to the output.

The thumbnail can be found in the generated FLZ file or uploaded to the printer with the job depending on if the slice or the print action was used.
